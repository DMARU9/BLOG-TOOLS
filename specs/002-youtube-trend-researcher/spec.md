# Feature Specification: YouTube Trend Researcher

**Feature Branch**: `002-youtube-trend-researcher`

**Created**: 2026-08-26

**Status**: Draft

**Input**: User description: "YouTube Trend Researcherを作成したい。TubeTrendを参考にしつつ、YouTube Data API + yt-dlp + LLM分析を自前の「YouTube Trend Researcher」にまとめる。外部から自然言語の指示（例：『Claude Codeで会社を回す方法を解説している動画で伸びているものを10個ピックアップし、文字起こしから伸びている理由をまとめ、共通して書かれている内容を表で教えて。直近半年以内・登録者少ないのに再生が伸びているものに絞って』）を受け取り、自律的にリサーチを実施する。単一能力に絞らず、OpenDeepResearchのように自分自身で複数の角度から検索できること。BLOG-TOOLS直下にYouTube_Trend_Researcherディレクトリを作成し、外部から依頼→ツール実行→アウトプット取得という使い方をする。GUIは現時点では不要。"

## Purpose

ブログ運用（DMARU9.github.io）のためのコンテンツ・リサーチを支援するツール。YouTube 上の「伸びている／トレンドの」動画を、ユーザーの意図を自然言語で与えるだけで自律的に探索・絞り込み・文字起こし・分析し、構造化されたリサーチレポートを返す。

参考とする既存の着想：
- **TubeTrend**: YouTube トレンド分析を API 取得・ダウンロード・分析で一体的に扱うという能力セットの参考。
- **OpenDeepResearch**: 単一検索に依存せず、エージェントが自ら複数の角度から検索・統合する「外部リクエスト → 実行 → アウトプット」の形の参考。

本ツールはこれらを統合し、BLOG-TOOLS 内の自己完結モジュールとして構築する。GUI は v1 では不要。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自然言語指示からの自律リサーチ実行 (Priority: P1)

ユーザーがトピックと条件を含む自然言語の指示を外部から与えると、ツールが検索・絞り込み・文字起こし・分析・統合を自律的に実行し、最終レポートを返す。人間の追加入力なしで完了することが価値の核心。

**Why this priority**: ツールの存在意義そのもの。これが実現できれば即座に価値を提供できる。

**Independent Test**: 指示「Claude Codeで会社を回す方法を解説している動画で伸びているものを10個ピックアップして」を与え、選定動画リストと分析を含む Markdown レポートが返されることを確認する。

**Acceptance Scenarios**:

1. **Given** ユーザーが自然言語指示を渡した, **When** ツールを実行した, **Then** 追加入力なしに最終レポートが返される
2. **Given** 指示にトピックと条件が含まれている, **When** ツールが実行された, **Then** 条件に合う動画が選定され、伸びている理由と共通点が分析される
3. **Given** レポートが返された, **When** 内容を確認した, **Then** 使用した動画のタイトル・URL・チャンネル・統計が明示されている

---

### User Story 2 - 複数角度からの自律的探索 (Priority: P1)

ツールは単一の検索クエリに依存せず、指示されたトピックから複数の検索角度・クエリを自動生成し、複数回にわたって YouTube を探索・統合する。これにより「ユーザーが各検索を手で指定しなくても」トピックの多面的な把握が得られる。

**Why this priority**: ユーザーが明示的に求めている差別化ポイント（「OpenDeepResearchのように自分に対していろいろな角度から検索ができる」）。単一検索ではこの価値を提供できない。

**Independent Test**: 同一のトピック指示に対し、内部的に複数の検索クエリ/角度が生成され、それらが統合されていることを中間成果物またはログで確認する。

**Acceptance Scenarios**:

1. **Given** トピック指示が与えられた, **When** ツールが検索を実行した, **Then** 1つのクエリではなく複数の角度からの検索が行われる
2. **Given** 複数の検索結果がある, **When** ツールが統合した, **Then** 重複が排除され、関連する動画が一貫した候補リストにまとめられる
3. **Given** 探索が不十分と判断された, **When** ツールが再検索を実行した, **Then** 追加の角度から補完が行われる

---

### User Story 3 - 外部リクエスト・実行・アウトプット取得のインターフェース (Priority: P2)

ツールは外部からの依頼を受け付け、実行し、構造化されたアウトプットを返す。GUI はなく、プログラムやコマンドから呼び出せる形とする（OpenDeepResearch の「外部から依頼 → 実行 → 取得」のイメージ）。

**Why this priority**: ユーザーが指定した利用形態の前提。ただし、中核となるリサーチ能力（US1・US2）があれば個別にも価値を検証できるため P2。

**Independent Test**: コマンド／API 経由で指示を渡し、規定の出力（Markdown レポート、または構造化データ）が返されることを確認する。

**Acceptance Scenarios**:

1. **Given** 外部から指示が渡された, **When** ツールが起動した, **Then** 指示を受け付けて実行を開始する
2. **Given** 実行が完了した, **When** 結果が返された, **Then** 構造化されたレポート（動画リスト・分析・共通点・出典）が含まれる
3. **Given** 出力形式が指定された, **When** レポート生成された, **Then** 指定された形式で出力される

---

### User Story 4 - 指示に基づく絞り込みと多様な出力形式 (Priority: P3)

ツールは指示から暗黙的・明示的なフィルタ条件（投稿日窓、登録者数閾値、再生数閾値、トピック関連性、件数など）を抽出し適用する。また、出力形式（表・要約・件数指定など）に従ってレポートを整形する。

**Why this priority**: 実用上重要だが、まずは「探索して分析する」中核能力があれば個別に検証可能。条件抽出とフォーマットは拡張性の一部として後続でも価値を発揮する。

**Independent Test**: 指示「直近半年以内・登録者が少ないのに再生が伸びているものに絞って、共通点は表でまとめて」を与え、フィルタが適用され、共通点が表形式で出力されることを確認する。

**Acceptance Scenarios**:

1. **Given** 指示に「直近半年以内」とある, **When** フィルタが適用された, **Then** 投稿日が窓外の動画は除外される
2. **Given** 指示に「登録者が少ないのに再生が伸びている」とある, **When** フィルタが適用された, **Then** 登録者数と再生数の関係で閾値を満たさない動画は除外される
3. **Given** 指示に「共通点は表で」とある, **When** レポートが生成された, **Then** 共通点が表形式で含まれる

---

### Edge Cases

- **YouTube Data API のクォータ超過**: リトライ・バックオフし、それでも不可の場合はユーザーに理解可能なメッセージを出して途中結果を返すか安全に終了する
- **文字起こし（字幕）が存在しない動画**: Whisper で音声文字起こしを試み（GPU 前提）、失敗時はメタデータのみの分析に切り替え、その旨をレポートに明記する
- **登録者数が非公開のチャンネル動画**: 候補から除外し、レポートの `notes` に除外理由を記録する（FR-004）
- **実行全体が 100 分を超過**: 途中までの候補・分析をまとめ、部分的な `ResearchReport` を返す
- **フィルタ条件に合う動画が0件**: 条件緩和の提案または「該当なし」を明示してレポートを返す
- **指定件数（例:10個）に満たない**: 実際に見つかった件数を報告し、不足を明記する
- **複数言語の字幕**: 優先言語を設定可能とし、フォールバック言語を備える
- **LLM の分析が根拠を欠く**: 主張に対して参照動画・該当箇所を紐付け、根拠のない断言を避ける
- **ネットワークエラー・タイムアウト**: 個別リクエスト単位でリトライし、長時間実行は全体の時間上限を設ける
- **指示が曖昧で探索方向が定まらない**: 実行可能な解釈で開始し、前提をレポートに記載する（必要に応じて確認ステップを設ける設計とする）

## Requirements *(mandatory)*

### Functional Requirements

**指示の受付と自律実行（オーケストレーション）**

- **FR-001**: システムは外部からの自然言語リサーチ指示（トピック・条件・出力指定を含む）を受け取り、最終レポートが产出されるまで自律的に実行しなければならない
- **FR-002**: システムは指示を複数のサブタスク（探索戦略の立案、動画取得と絞り込み、文字起こし、LLM 分析、統合とフォーマット）に分解し、エージェント的なオーケストレーションで実行しなければならない

**複数角度からの探索（YouTube Data API）**

- **FR-003**: システムは指示のトピックから複数の検索クエリ／角度を自動生成し、yt-dlp（`ytsearch` / `ytsearchdate`）を用いて複数回検索しなければならない（単一クエリへの依存は禁止）。YouTube Data API はオプションのフォールバック。
- **FR-004**: システムは yt-dlp を用いて動画メタデータ・統計（再生数、投稿日）およびチャンネルの登録者数（`channel_follower_count`）を取得しなければならない。登録者数が非公開（`None`）の場合は、その動画を候補から**除外**する（補完・推定は行わない）。

**絞り込みと文字起こし**

- **FR-005**: システムは指示から抽出したフィルタ条件（投稿日窓、登録者数閾値、再生数閾値、トピック関連性、件数など）を動画候補に適用しなければならない。既定の「伸びている」判定は視聴ベロシティ（再生数÷登録者数）≥ 10.0 かつ 直近半年（180日）以内とする（subscriber_count が取得できない動画は FR-004 により事前除外済み）。
- **FR-006**: システムは yt-dlp を用いて選定候補の文字起こし（字幕／トランスクリプト）を抽出し、言語フォールバックを備えなければならない。字幕がない場合は Whisper で音声文字起こしを行う（GPU 前提）。

**LLM 分析と統合**

- **FR-007**: システムは LLM 分析を用いて、各動画の「伸びている理由／傾向」を導出しなければならない。LLM 出力はプロンプトで指示し、軽いパース関数で構造化して後続へ渡す。
- **FR-008**: システムは選定動画間で共通して語られている内容・テーマを特定し、要約しなければならない。v1 では動画本文（字幕/Whisper 文字起こし）のみを対象とし、コメントは利用しない。
- **FR-009**: システムは指示の出力指定（表、要約、件数など）に従って最終レポートを整形しなければならない。デフォルト出力は Markdown とする

**外部インターフェースと堅牢性**

- **FR-010**: システムは実行結果（選定動画リスト、分析、共通点の表、出典 URL）を外部リクエスト元へ返却しなければならない
- **FR-011**: システムはエラー（API クォータ、文字起こし欠損、該当0件、ネットワーク障害）を適切に処理し、ユーザーに理解可能なメッセージを出さなければならない
- **FR-012**: システムは中間成果物（候補リスト、文字起こし、分析結果）を永続化し、透明性と再現性を担保しなければならない

### Key Entities *(include if feature involves data)*

- **ResearchInstruction**: ユーザーからの自然言語指示。トピック、暗黙的・明示的フィルタ条件（投稿日窓・登録者数上限・再生数下限・velocity_ratio・件数等）、出力形式指定を含む
- **VideoCandidate**: 動画ID、タイトル、URL、チャンネルID、チャンネル名、投稿日、再生数、登録者数、関連度スコア（velocity_ratio を含む）を属性に持つ
- **Transcript**: 動画ID、言語、テキスト（またはセグメント）を属性に持つ
- **AnalysisFinding**: 個別動画の「伸びている理由」、および複数動画間の共通テーマを表す
- **ResearchReport**: 選定動画リスト、個別分析、共通点の表、出典 URL をまとめた最終アウトプット

## Clarifications

### Session 2026-08-26（第1ラウンド：clarity 確定）

- Q: 「伸びている動画」の自動判定における既定の閾値は？ → A: 視聴ベロシティ（再生数 ÷ 登録者数）≥ 10.0 かつ 投稿日が直近半年（180日）以内を既定とする。指示で上書き可。
- Q: 字幕がない動画の Whisper 文字起こしをどの環境で実行するか？ → A: GPU（CUDA）利用可能な環境を前提とし、base/medium モデルも許容する。
- Q: コメント取得（youtube-comment-downloader）を分析にどう組み込むか？ → A: v1 ではコメントを取得しない。youtube-comment-downloader は未導入（将来拡張想定のみ）。
- Q: LLM の分析結果の出力形態は？ → A: プロンプトで指示しつつ、堅牢性のため軽いパース関数で Markdown/JSON を抽出して後続へ渡す（構造化出力強制はしない）。
- Q: 自律実行の全体時間上限は？ → A: 全体の実行を 10 分で上限とし、超過時は途中結果を返す。

### Session 2026-08-26（第2ラウンド：指摘反映）

- Q: `ytsearchdate` の前提は？ → A: 検索は `ytsearchN:` のみとし、日付絞り込みは取得後の `upload_date` パースで行う。`ytsearchdate` は日付指定であり「直近N日」窓ではない（research.md R-1 に追記）。
- Q: `subscriber_count` 非公開時の velocity 判定は？ → A: **非公開チャンネル動画は対象外とする**（candidates から除外）。取得できた動画のみ velocity≥10.0 を適用。
- Q: 既定閾値の矛盾（5.0 vs 10.0）は？ → A: **velocity≥10.0 かつ 直近半年以内が正**。report-schema サンプルの 5.0 を 10.0 に統一。
- Q: LLM 並列実行数の上限は？ → A: **並列実行数の上限は 2**（analyze_content 等の同時 LLM 呼び出し）。
- Q: 実行時間上限は？ → A: 全体の実行を **100 分**に引き上げる（超過時は途中結果を返す）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 1回の自然言語指示で、追加の人間入力なしに完全なリサーチレポートが产出される
- **SC-002**: レポートには使用した動画（タイトル・URL・チャンネル・統計）が明示される
- **SC-003**: 指示のフィルタ条件（投稿日窓・登録者数／再生数閾値等）が正確に適用される（例：直近半年以内かつ低登録者高再生の絞り込みが守られる）
- **SC-004**: 出力形式指定（例：共通点を表で）が守られ、要求された構造が出力に含まれる
- **SC-005**: 外部リクエストから最終アウトプット取得まで、全体実行時間上限（100 分）内に完了する
- **SC-006**: ユーザーが各検索を手で指定せずとも、ツールが自ら複数角度からトピックを探索できる

## Assumptions

- **YouTube Data API キーは任意**（v1 ではコメントを取得せず、登録者数は yt-dlp の `channel_follower_count` から取得。非公開時はその動画を対象外とする）。キーがある場合のみオプション取得のフォールバックに利用。
- LLM バックエンドは設定可能（LangChain の LLM 抽象化等）とし、既定は `openai:mimo-v2.5`（OpenDeepResearch 設定をコピー）。
- ツールは CLI またはプログラム API で呼び出される。v1 は GUI を含まない（OpenDeepResearch 的「外部リクエスト → 実行 → 取得」の形）。
- BLOG-TOOLS 内の自己完結モジュールとして構築し、DMARU9.github.io のブログ記事リサーチ用途に寄与する（Constitution 準拠）。
- 実行環境に yt-dlp および ffmpeg が利用可能。Whisper は **GPU（CUDA）前提**。
- LLM 並列実行数の上限は **2**。全体実行時間の上限は **100 分**（超過時は途中結果を返す）。
- API のレートリミット／クォータはリトライ・バックオフで扱う。
- 実装ディレクトリは `BLOG-TOOLS/YouTube_Trend_Researcher/` を想定する。
