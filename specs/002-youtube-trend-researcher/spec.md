# Feature Specification: YouTube Trend Researcher

**Feature Branch**: `002-youtube-trend-researcher`

**Created**: 2026-08-26

**Status**: Draft

**Input**: User description: "YouTube Trend Researcherを作成したい。TubeTrendを参考にしつつ、yt-dlp + LLM分析を自前の「YouTube Trend Researcher」にまとめる。外部から自然言語の指示（例：『Claude Codeで会社を回す方法を解説している動画で伸びているものを10個ピックアップし、文字起こしから伸びている理由をまとめ、共通して書かれている内容を表で教えて。直近半年以内・登録者少ないのに再生が伸びているものに絞って』）を受け取り、自律的にリサーチを実施する。単一能力に絞らず、OpenDeepResearchのように自分自身で複数の角度から検索できること。BLOG-TOOLS直下にyoutube_trend_researcherディレクトリを作成し、外部から依頼→ツール実行→アウトプット取得という使い方をする。GUIは現時点では不要。"

## Purpose

ブログ運用（DMARU9.github.io）のためのコンテンツ・リサーチを支援するツール。ユーザーがブログ記事の執筆に参考にしたいトピックを自然言語で与えるだけで、関連する動画を自律的に探索・文字起こし・要約し、ブログ執筆の参考となるリサーチレポートを返す。

参考とする既存の着想：
- **OpenDeepResearch**: 単一検索に依存せず、エージェントが自ら複数の角度から検索・統合する「外部リクエスト → 実行 → アウトプット」の形の参考。

本ツールはこれを統合し、BLOG-TOOLS 内の自己完結モジュールとして構築する。GUI は v1 では不要。「トレンド／伸びているか」の判定は行わず、yt-dlp の関連度順検索結果の上位 N 件を解析対象とする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自然言語指示からの自律リサーチ実行 (Priority: P1)

ユーザーがトピックと条件を含む自然言語の指示を外部から与えると、ツールが検索・絞り込み・文字起こし・分析・統合を自律的に実行し、最終レポートを返す。人間の追加入力なしで完了することが価値の核心。

**Why this priority**: ツールの存在意義そのもの。これが実現できれば即座に価値を提供できる。

**Independent Test**: 指示「Claude Codeで会社を回す方法を解説している動画を参考にブログを書きたい。5個ピックアップして」を与え、選定動画リストとブログ執筆用の要約・共通ネタを含む Markdown レポートが返されることを確認する。

**Acceptance Scenarios**:

1. **Given** ユーザーが自然言語指示を渡した, **When** ツールを実行した, **Then** 追加入力なしに最終レポートが返される
2. **Given** 指示にトピックと件数が含まれている, **When** ツールが実行された, **Then** 関連度順の上位 N 件が選定され、ブログ執筆の参考となる要約と共通ネタが分析される
3. **Given** レポートが返された, **When** 内容を確認した, **Then** 使用した動画のタイトル・URL・チャンネル・統計が明示されている

---

### User Story 2 - 複数角度からの自律的探索 (Priority: P4, 将来拡張)

ツールは単一の検索クエリに依存せず、指示されたトピックから複数の検索角度・クエリを自動生成し、複数回にわたって YouTube を探索・統合する。これにより「ユーザーが各検索を手で指定しなくても」トピックの多面的な把握が得られる。**ただし、現在のフェーズ（v1）では実装せず、将来拡張として予約する**（第4ラウンド clarify で確定）。

**Why this priority**: ユーザーが明示的に求めている差別化ポイント（「OpenDeepResearchのように自分に対していろいろな角度から検索ができる」）。単一検索ではこの価値を提供できない。

**Independent Test**: 同一のトピック指示に対し、内部的に複数の検索クエリ/角度が生成され、それらが統合されていることを中間成果物またはログで確認する。

**Acceptance Scenarios**:

1. **Given** トピック指示が与えられた, **When** ツールが検索を実行した, **Then** 1つのクエリではなく複数の角度からの検索が行われる
2. **Given** 複数の検索結果がある, **When** ツールが統合した, **Then** 重複が排除され、関連する動画が一貫した候補リストにまとめられる
3. **Given** 探索が不十分と判断された, **When** ツールが再検索を実行した, **Then** 追加の角度から補完が行われる

---

### User Story 3 - 外部リクエスト・実行・アウトプット取得のインターフェース (Priority: P2)

ツールは外部からの依頼を受け付け、実行し、構造化されたアウトプットを返す。GUI はなく、プログラムやコマンドから呼び出せる形とする（OpenDeepResearch の「外部から依頼 → 実行 → 取得」のイメージ）。

**Why this priority**: ユーザーが指定した利用形態の前提。ただし、中核となるリサーチ能力（US1・US2）があれば個別にも価値を検証できるため P2。

**Independent Test**: コマンド／API 経由で指示を渡し、規定の出力（Markdown レポート、または構造化データ）が返されることを確認する。

**Acceptance Scenarios**:

1. **Given** 外部から指示が渡された, **When** ツールが起動した, **Then** 指示を受け付けて実行を開始する
2. **Given** 実行が完了した, **When** 結果が返された, **Then** 構造化されたレポート（動画リスト・分析・共通点・出典）が含まれる
3. **Given** 出力形式が指定された, **When** レポート生成された, **Then** 指定された形式で出力される

---

### User Story 4 - 件数指定と多様な出力形式 (Priority: P3)

ツールは指示から解析対象の件数（明示的または暗黙的）を抽出する。指定がない場合は既定の 5 件とする。また、出力形式（表・要約・件数指定など）に従ってレポートを整形する。「トレンド／伸びているか」の判定は行わず、yt-dlp の検索結果（関連度順）の上位 N 件を対象とする。

**Why this priority**: 実用上重要だが、まずは「探索して要約する」中核能力があれば個別に検証可能。件数抽出とフォーマットは拡張性の一部として後続でも価値を発揮する。

**Independent Test**: 指示「Claude Code の便利な使い方を解説している動画を参考にブログを書きたい。共通して語られているネタは表でまとめて」を与え、関連度上位 5 件が選定され、共通ネタが表形式で出力されることを確認する。

**Acceptance Scenarios**:

1. **Given** 指示に「10個」とある, **When** 対象が選定された, **Then** 関連度順の上位 10 件が解析対象となる
2. **Given** 指示に件数がない, **When** 対象が選定された, **Then** 既定の 5 件が解析対象となる
3. **Given** 指示に「共通点は表で」とある, **When** レポートが生成された, **Then** 共通ネタが表形式で含まれる

---

### Edge Cases

- **YouTube Data API は利用しない**: データ取得はすべて yt-dlp で行う。API キー・クォータ管理は一切不要（第5ラウンド clarify で確定）。
- **文字起こし（字幕）は必ず取得できる**: yt-dlp は自動翻訳字幕（自動生成キャプションの翻訳）も取得できるため、字幕欠損は基本的に起こらない。取得できない場合のみ `notes` に記録する（Whisper は利用しない）。
- **実行全体が 100 分を超過**: 途中までの候補・分析をまとめ、部分的な `ResearchReport` を返す
- **該当動画が0件**: 「該当なし」を明示してレポートを返す
- **指定件数（例:10個）に満たない**: 実際に見つかった件数を報告し、不足を明記する
- **複数言語の字幕**: 優先言語を設定可能とし、フォールバック言語を備える
- **LLM の要約が根拠を欠く**: ブログ参考用の主張に対して参照動画・該当箇所を紐付け、根拠のない断言を避ける
- **ネットワークエラー・タイムアウト**: 個別リクエスト単位でリトライし、長時間実行は全体の時間上限を設ける
- **指示が曖昧で探索方向が定まらない**: 実行可能な解釈で開始し、前提をレポートに記載する（必要に応じて確認ステップを設ける設計とする）

## Requirements *(mandatory)*

### Functional Requirements

**指示の受付と自律実行（オーケストレーション）**

- **FR-001**: システムは CLI 経由で外部からの自然言語リサーチ指示（トピック・条件・出力指定を含む）を受け取り、最終レポートが产出されるまで自律的に実行しなければならない。プログラム API 経由の呼び出しは将来拡張（第4ラウンド clarify で確定）。
- **FR-002**: システムは指示を複数のサブタスク（探索戦略の立案、動画取得と絞り込み、文字起こし、LLM 分析、統合とフォーマット）に分解し、エージェント的なオーケストレーションで実行しなければならない

**複数角度からの探索**

- **FR-003**: システムは LLM を用いて指示文から検索クエリ（トピック選定を含む）を1つ生成し、yt-dlp（`ytsearchN:`）で1回検索しなければならない。N は `FR-005` の件数とする。トピックの選定・クエリ化は AI（LLM）に委ねる（第4ラウンド clarify で確定）。検索結果は関連度順で返される。複数角度からの自動検索は将来拡張（US2）。YouTube Data API は **利用しない**（第5ラウンド clarify）。
- **FR-004**: システムは yt-dlp を用いて動画メタデータ・統計（再生数、投稿日、チャンネル名等）を取得しなければならない。「トレンド／伸びているか」の判定は行わず、関連度順の検索結果をそのまま利用する。

**絞り込みと文字起こし**

- **FR-005**: システムは yt-dlp の検索結果（関連度順）から、上位 N 件を解析対象として選定しなければならない。N は指示に件数指定があればその値、なければ既定の **5 件**とする。トレンド判定や再生数・登録者数による絞り込みは行わない。
- **FR-006**: システムは yt-dlp を用いて、選定した上位 N 件（既定 5 件）の文字起こし（字幕／トランスクリプト）を抽出し、言語フォールバック（自動翻訳字幕を含む）を備えなければならない。字幕は自動翻訳により原則として必ず取得できるため、欠損は想定しない。Whisper による音声文字起こしは行わない（第4・第5ラウンド clarify で確定）。

**LLM 分析と統合**

- **FR-007**: システムは LLM 分析を用いて、各動画の内容を「ブログ記事執筆の参考」として要約・洞察しなければならない。LLM 出力はプロンプトで指示し、軽いパース関数で構造化して後続へ渡す。
- **FR-008**: システムは選定動画間で共通して語られている内容・テーマを特定し、ブログ記事で取り上げるべき共通ネタとして要約しなければならない。v1 では動画本文（字幕取得テキスト）のみを対象とし、コメントは利用しない。
- **FR-009**: システムは指示の出力指定（表、要約、件数など）に従って最終レポートを整形しなければならない。デフォルト出力は Markdown とする。v1 のレポート構成は「選定動画リスト」「各動画のブログ執筆向け要約」「動画間の共通ネタ（表）」とし、執筆ヒント／アウトライン案は含めない（第4ラウンド clarify で確定）。

**外部インターフェースと堅牢性**

- **FR-010**: システムは実行結果（選定動画リスト、ブログ執筆用の要約・分析、共通ネタの表、出典 URL）を CLI の標準出力（または指定ファイル）へ返却しなければならない
- **FR-011**: システムはエラー（該当0件、ネットワーク障害等）を適切に処理し、ユーザーに理解可能なメッセージを出さなければならない
- **FR-012**: システムは中間成果物（候補リスト、文字起こし、分析結果）を永続化し、透明性と再現性を担保しなければならない
- **FR-013**: システムは CLI 実行時に、どのノード（処理段階）にいるか、およびどのノードの処理を実施中かを進捗表示しなければならない。進捗は各ノードの開始・完了ごとに標準エラー出力（stderr）へ出力し、最終レポート（stdout）と分離する。進捗表示と最終結果の間に、エラーまたは成功メッセージのみが表示される空白状態を作ってはならない（第4ラウンド clarify で確定）。

### Key Entities *(include if feature involves data)*

- **ResearchInstruction**: ユーザーからの自然言語指示。トピック、解析対象件数（明示・暗黙、既定 5 件）、出力形式指定を含む
- **VideoCandidate**: 動画ID、タイトル、URL、チャンネルID、チャンネル名、投稿日、再生数、関連度順の順位を属性に持つ
- **Transcript**: 動画ID、言語、テキスト（またはセグメント）を属性に持つ
- **AnalysisFinding**: 個別動画の「ブログ執筆の参考となる要約・洞察」、および複数動画間の共通ネタを表す
- **ResearchReport**: 選定動画リスト、ブログ執筆用の要約・分析、共通ネタの表、出典 URL をまとめた最終アウトプット

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 1回の自然言語指示で、追加の人間入力なしに完全なリサーチレポートが产出される
- **SC-002**: レポートには使用した動画（タイトル・URL・チャンネル・統計）が明示される
- **SC-003**: 指示の件数指定が正確に反映される（指定なしは既定 5 件、指定ありはその件数分の関連度上位動画が解析対象となる）
- **SC-004**: 出力形式指定（例：共通点を表で）が守られ、要求された構造が出力に含まれる
- **SC-005**: 外部リクエストから最終アウトプット取得まで、全体実行時間上限（100 分）内に完了する
- **SC-006**: ユーザーが各検索を手で指定せずとも、指示文から単一クエリ検索で関連度上位 N 件を自動選定し、要約・共通ネタ抽出まで完了する（複数角度探索は将来拡張／US2 参照）

## Assumptions

- **YouTube Data API は利用しない**（第5ラウンド clarify）。データ取得はすべて yt-dlp で行い、API キー・クォータ管理は一切不要。トレンド判定は行わず、yt-dlp の関連度順検索結果を利用する。
- LLM バックエンドは設定可能（LangChain の LLM 抽象化等）とし、既定は `openai:mimo-v2.5`（OpenDeepResearch 設定をコピー）。
